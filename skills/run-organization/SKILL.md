# Run Organisation (Virtual Biotech harness)

This local skill replaces the upstream `run-organization` skill: the standard
is the same, but the layout below is what *this* harness actually writes.

> **Every run must be understandable by someone who was not there, opening the
> directory cold, six months later.**

## The run directory

Every session gets one directory (its absolute path is in the Session section
of your system prompt). Paths starting with `work/`, `inputs/`, `evidence/`,
`report/`, `logs/` or `.claude/` resolve to it.

```
runs/<RUN_ID>/
├── MANIFEST.json        run status, pinned config, every artifact (sha256, producing agent,
│                        producing tool call, citing claims) — rewritten after every turn
├── README.md            generated map of the run — rewritten after every turn; do not hand-edit
├── audit.html           self-contained audit report — rewritten after every turn
├── session_report.json  turns, agents, costs, tool failures
├── inputs/
│   ├── query.txt        every user turn, verbatim
│   ├── plan.json        the analysis plan                      ← you write this (write_plan)
│   ├── config.json      pinned config: models, prompt hashes, MCP servers, git commits
│   └── environment.txt  installed packages (the upstream prompts call it environment_full.yml)
├── work/<agent>/        one subtree per specialist — never flat
│   ├── code/scripts/
│   ├── data/{raw,processed}/
│   └── results/{figures,tables,reports}/
├── work/_mcp/data/processed/   files saved by MCP data tools
├── evidence/
│   ├── artifacts.json   registered artifacts (mcp__provenance__register_artifact)
│   ├── claims.json      claim → evidence                       ← you write this (record_claims)
│   └── provenance.json  tool call → agent index, derived from the trace
├── memory/<agent>/MEMORY.md   per-role notes kept across delegations (UpdateMemory)
├── .claude/skills/      the skills used in this run (read-only copies)
├── logs/                trace.jsonl, cost_report.json, transcript.md, agent transcripts,
│                        MCP server logs (logs/mcp/), spilled tool outputs
└── report/              FINAL_REPORT.md (+ rendered copy with claim anchors resolved)
```

`MANIFEST.json`, `README.md`, `audit.html`, `session_report.json`,
`inputs/config.json`, `evidence/artifacts.json` and `evidence/provenance.json`
are generated by the harness. Your two responsibilities are **`plan.json`**
and **`claims.json`**, both written through provenance tools — the CSO has no
`Write` or `Bash` in this harness, and you do not need them.

Files written outside `work/<agent>/` are still captured and attributed, and
listed as misplaced in the MANIFEST; that is a defect for the next reader.

## 1. Declare the plan before dispatching

Before dispatching two or more specialists, call `mcp__provenance__write_plan`:

```python
write_plan(
  goal="Assess the safety risk of targeting IL-33 in asthma",
  steps=[
    {"id": "s1", "agent": "single-cell-analyst",
     "task": "IL33/IL1RL1 expression across lung and critical-organ cell types",
     "depends_on": [], "expected_outputs": ["il33_celltype_expression.csv"]},
    {"id": "s2", "agent": "fda-safety-officer",
     "task": "Clinical precedent AEs read against the expression profile",
     "depends_on": ["s1"]},
  ])
```

- `depends_on: []` → can start immediately; independent steps run in parallel
  (several `Task` calls in one response).
- Use `depends_on` only for real data dependencies.
- The plan is validated on write (cycles, unknown ids, duplicates). Fix and
  call again if it returns `ok: false`.
- **Deviating is allowed and expected** — deviations are recorded (the harness
  reconciles the plan against what actually ran each turn), not forbidden. If
  the change is substantial, call `write_plan` again.
- Skip the plan for single-specialist queries and clarification exchanges.

## 2. Keep artifacts in the right place

Each specialist writes only under `work/<its-own-name>/`. When a specialist
needs an earlier output, **give it the run-relative path**:

```
Load the expression table from
work/single-cell-analyst/results/tables/il33_celltype_expression.csv
```

Name for content, never for sequence or status: `il33_celltype_expression.csv`,
not `analysis2.csv` or `results_final_v3.csv`.

## 3. File claim-evidence objects

Every substantive factual assertion in your synthesis becomes a claim with the
evidence behind it (specialists produce citable artifacts with the
`evidence-citation` skill).

1. `mcp__provenance__list_artifacts` — get the exact run-relative paths. Do not
   guess a filename.
2. Write your synthesis with inline anchors:
   `...highly expressed in lung mast cells[[claim:C1]]...`
3. `mcp__provenance__record_claims` with the claim objects:

```python
record_claims(claims=[
  {"id": "C1",
   "text": "IL1RL1 is most highly expressed in lung mast cells (mean 2.4 CPM)",
   "agent": "single-cell-analyst",
   "confidence": "strong",
   "evidence": [
     {"kind": "table",
      "path": "work/single-cell-analyst/results/tables/il33_celltype_expression.csv",
      "note": "row: mast cell"},
     {"kind": "tool_call", "tool_use_id": "toolu_01..."}]}])
```

- Evidence is validated on write: `ok: false` means a path or tool id is wrong
  (or a cited tool call failed) — fix it and call again.
- **Never resolve a rejection by deleting the evidence.** A claim you cannot
  support is a finding: state it as unsupported or uncertain.
- `confidence`: `strong` = direct measurement; `moderate` = inference;
  `weak` = suggestive or indirect.
- Keep claim ids unique across turns; refile a revised claim with current evidence.
- Every `[[claim:Cn]]` anchor must match a filed claim; dangling anchors are
  reported as defects in README.md and by `vbt verify`.

## 4. End-of-turn checklist

- [ ] `write_plan` called, if two or more specialists ran
- [ ] Scientific review done where the review policy requires it
- [ ] Every substantive assertion carries a `[[claim:Cn]]` anchor
- [ ] `record_claims` returned `ok: true` for all of them
- [ ] `list_artifacts` shows no unexplained files
- [ ] Failed data sources and anything you could not establish are stated as gaps

## Anti-patterns

- Filing a claim with stretched evidence to clear the checklist (`weak` with a
  real artifact beats `strong` with a stretched one).
- Citing a specialist's prose: if no file or tool call backs a number, report it
  as unsupported or send the specialist back to produce the artifact.
- One claim covering a whole paragraph: one claim = one checkable assertion.
- Silently dropping a failed analysis: say so, and adjust your confidence.
